# COD production audit - 2026-08-10

## Outcome

The deployed product is viable as a controlled pilot for Web chat, model selection, wallet and expiring-credit settlement, synchronized tasks, desktop project access, and compute-market lead collection. The audit found no dependency vulnerabilities and no active usage reservations. It did find several gaps where the UI or capability API implied more than production could deliver. Those gaps are closed in this release.

This report distinguishes verified behavior from external integrations that still require credentials or provider contracts.

## Live baseline inspected

- Host: Ubuntu server at `95.41.23.60`, reached publicly through the `https://cod.kai.com` AWS ingress.
- Services: Nginx, PostgreSQL, `cod-control-plane`, health timer, and backup timer were active.
- Health: `/health` and `/ready` returned healthy PostgreSQL-backed status.
- Model gateway: `ai.kai.com` was live and exposed 17 unique catalog models, mirrored across two display sources as 34 source/model rows at final verification time.
- Wallet data: two users, no pending payment orders, no reserved usage, and no running tasks.
- External modes: payment collection, Feishu, and WeCom were unavailable because their production adapters or credentials were not configured.
- Browser verification: desktop workspace, task history, source/model selection, wallet, credit grants, ledger, theme, and inspector controls rendered without console errors.

## Findings closed by this release

| Severity | Finding | Resolution |
| --- | --- | --- |
| High | Mobile CSS hid both source and model selectors | The existing selectors now remain visible in a compact responsive header with no duplicate controls. |
| High | The API advertised payment-order support and accepted pending orders even though no payment adapter could complete them | `orderApi` now reflects the verified webhook configuration, and order creation returns `payments_unavailable` until the adapter is configured. |
| High | Public registration could issue trial credit without an invitation or verified email | Production registration is now explicitly configured and requires an existing user's immutable invite code. Existing users can retrieve and copy that code from the account panel. |
| Medium | A task could be marked complete without a result or failed without an error | Both memory and PostgreSQL stores now enforce terminal-state outcomes. Retry clears stale outcomes, and manual completion records an explicit user-confirmed result. |
| Medium | Hidden browser tabs continued task polling and device heartbeat calls | Web and mobile polling pauses while hidden and synchronizes immediately when visible; desktop behavior is preserved. |
| Medium | The capability API described buffered SSE as generic streaming | It now reports `streamingMode: buffered-sse`; progressive upstream streaming is not claimed. |
| Medium | API JSON could be cached by intermediaries or a direct client | JSON responses now carry `Cache-Control: no-store` and `X-Content-Type-Options: nosniff`. |
| Medium | The origin Nginx disclosed its exact version and the service sandbox could be tighter | Origin Nginx version tokens are disabled and systemd receives additional device, kernel, privilege, address-family, and umask restrictions. The outer HTTPS ingress header remains listed below. |
| Low | The account panel offered no explanation when wallet funding was unavailable | It now states that COD will not create unpayable orders and that only existing wallet and trial credit can be used. |

## Verification gates

The following checks passed locally on the release source:

- TypeScript type checks for Web, Desktop, and control plane.
- ESLint with zero warnings.
- 50 automated tests: 15 Web tests and 35 control-plane tests.
- Production builds for Web, Desktop TypeScript, and control plane.
- Production dependency audit with zero known vulnerabilities.
- Git whitespace validation.

The deployment script repeats type checks, tests, lint, builds, dependency audit, Nginx validation, readiness checks, atomic activation, and rollback handling on the server.

## Verified functional loops

1. Password login or invite-only registration -> signed session -> account, model catalog, and device registration.
2. Source/model selection -> source-bound request -> pre-authorized funds -> upstream answer -> immutable usage settlement -> wallet and grant refresh.
3. Task creation -> target-device synchronization -> running state -> result or error -> terminal state visible from other clients.
4. Existing user invite code -> new-user registration -> one trial grant -> permanent referral binding.
5. Mobile viewport -> visible source and model switching -> normal chat or model comparison.
6. Health and readiness -> systemd service -> Nginx -> public HTTPS application.

## External blockers and residual risks

- Payment collection is not live. A real WeChat or Alipay checkout adapter, provider-side webhook translation, reconciliation, refunds, invoices, settlement, and anti-fraud process are still required. COD now fails closed instead of creating a dead order.
- The origin at `95.41.23.60` now returns only `Server: nginx`, but the AWS HTTPS ingress for `cod.kai.com` still emits an exact Nginx version. That outer load-balancer or ingress configuration must be hardened separately.
- Feishu and WeCom require application credentials, verified user bindings, and live round-trip acceptance. Their unavailable state remains explicit.
- KAI Wiki requires its production search endpoint, key, ACL contract, and a retrieval-quality benchmark before it can be declared live.
- Hong Kong product launch requires the receiving product to accept the signed assertion and finalize its frame, cookie, logout, and CSP contract.
- Current SSE is emitted after the upstream response is complete. True token-by-token streaming and TTFT measurement remain future work.
- The browser session token is stored in local storage. The CSP materially reduces exposure, but a future Web-specific HttpOnly cookie or narrower scoped token would further reduce XSS impact.
- Public desktop and mobile distribution still requires organization-owned Apple, Windows, and Android signing credentials and release-channel acceptance tests.
- The coding Agent intentionally executes approved local developer tools. Its project-root checks and permission UI reduce risk but cannot make arbitrary code execution risk-free.

No blocked integration is represented as live, funded, or complete in this release.
