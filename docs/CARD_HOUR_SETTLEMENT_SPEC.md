# COD 卡时统一结算规范

> 状态：V2 结算唯一口径（2026-08-13）
> 适用范围：模型调用、代码任务、算力租赁、托管服务、商品、优惠、退款与后续接入的所有 COD 内部服务

## 1. 核心规则

1. COD 系统内所有商品和服务只使用“COD 卡时”标价、报价、扣减、退款和结算。
2. 商品由人民币价格迁移为卡时价格时，数值保持一致，只替换单位。例如原价 `¥64.60 / 日` 的商品，在 COD 中标为 `64.60 卡时 / 日`，订单扣减 `64.60 卡时`。
3. `1 卡时` 的人民币购买成本固定为 `¥1.002`。其中 `¥1.000` 对应卡时面值，`¥0.002` 是 COD 的千分之二平台服务计提。
4. 千分之二已经包含在卡时购买单价里，用户购买卡时或使用卡时时都不再支付、也不再看到一笔独立手续费。
5. `1.002` 只用于人民币购买卡时的换算，绝不能再次乘到商品卡时价或系统内订单上。
6. 人民币只存在于外部支付购买卡时及相关退款、发票和财务对账；人民币钱包不能直接支付系统内商品或服务。
7. 人民币到卡时是单向入口。卡时不能兑换、出售或提现为人民币，也不承诺任何法币回购价值。
8. 卡时可以在 COD 平台内交易、转让和用于结算；交易前后资产单位始终是卡时，只发生平台卡时账本账户之间的转移。

## 2. 唯一计算公式

内部卡时精度为千分之一：`1 卡时 = 1000 cardHoursMilli`。人民币支付以整数分落账，换算过程使用整数，禁止浮点金额。

### 2.1 商品价格迁移

```ts
// 原人民币价格和新卡时价格使用相同的千分位整数数值，只改变单位语义。
priceCardHoursMilli = legacyPriceCnyMilli
```

示例：`¥64.60` 即 `64_600 priceCnyMilli`，迁移后为 `64_600 priceCardHoursMilli`，展示 `64.60 卡时`。

### 2.2 系统内订单

```ts
subtotalCardHoursMilli = sum(line.priceCardHoursMilli * line.quantity)
chargedCardHoursMilli = max(0, subtotalCardHoursMilli - discountCardHoursMilli)
```

系统内订单不会乘 `1.002`。例如商品价 `64.600 卡时`、无优惠，用户账户就扣 `64.600 卡时`。

### 2.3 人民币购买卡时

```ts
const CARD_HOUR_MILLI_CNY = 1002;
const CARD_HOUR_MILLI_UNITS = 1000;

paymentCents = ceil(
  purchasedCardHoursMilli * CARD_HOUR_MILLI_CNY
  / (CARD_HOUR_MILLI_UNITS * 10)
)
```

购买 `100.000 卡时` 的精确人民币成本为 `¥100.200`；支付 `¥100.20`，到账 `100.000 卡时`，不再另收手续费。支付渠道只支持分时，最终卡时包应使用能得到明确分金额的固定档位，服务端在整张购买订单上只取整一次。

## 3. 展示规则

- 商品卡：`64.60 卡时 / 日`，不显示同一商品的人民币结算价。
- 订单合计：`应付 64.60 卡时`。
- 卡时购买页：`100 卡时 · 支付 ¥100.20`，可辅助说明“价格已含平台服务”，不得出现 `+ 手续费`。
- 系统内订单流水只显示卡时扣减；卡时购买流水分别记录人民币支付和卡时到账，但不能混成一次商品扣费。
- 卡时不足时，操作是“购买卡时”，不是“使用人民币钱包补差额”。购买成功后回到原订单重新确认。
- 资产页可展示“可用 / 交易冻结 / 待入账”卡时和平台内交易入口，但不得出现“提现”“兑回人民币”或人民币估值承诺。
- 所有端都由服务端返回整数值并使用共享格式化函数，客户端不得自行换算或修改应付数量。

## 4. 账本规则

系统内商品订单与卡时购买订单是两类独立账本事件。

### 4.1 系统内商品订单

```text
用户卡时账户       -64.600
服务清算账户       +64.600
合计                 0
```

### 4.2 购买卡时

```text
外部支付订单       ¥100.200
用户卡时账户       +100.000
平台服务计提         ¥0.200
```

### 4.3 平台内卡时交易

直接转让或已完成交易必须在同一事务中原子过账：

```text
转出方可用卡时账户   -20.000
转入方可用卡时账户   +20.000
合计                   0
```

需要交付确认的交易先冻结再清算：创建交易时将转出方卡时从“可用”移动到“交易冻结”，完成时转入接收方，取消/超时则原额解冻。任何一步都不创建人民币应收或可提现余额。

- 每次扣减、发放或退款都必须原子执行并绑定唯一 `settlementId`。
- 用户卡时不足时，系统内订单整笔失败，不得部分扣卡时后再从人民币余额补差额。
- 相同幂等键不得产生第二次扣减或第二次发放。
- 管理员测试账户可以免扣，但仍写入 `billing_exempt` 零扣减审计，并保留应扣卡时。
- 优惠直接减少订单卡时价，不参与人民币换算。
- 系统内订单退款退回卡时；交易取消解冻或退回卡时，绝不产生人民币退款。
- 只有撤销原卡时购买订单时才可原路退人民币，而且对应卡时必须仍未使用、未转出、未冻结并被同步回收。这是购卡订单撤销，不是卡时兑换；两类退款不得串账。
- 每批卡时保留来源、获得时间和有效期。转让或交易时按最早到期批次转出，并把原到期时间与来源链传给接收方，禁止通过交易延长有效期或洗掉审计来源。

## 5. 字段命名

```ts
interface CardHourPrice {
  subtotalCardHoursMilli: number;
  discountCardHoursMilli: number;
  chargedCardHoursMilli: number;
}

interface CardHourPurchase {
  purchasedCardHoursMilli: number;
  paymentCents: number;
  cardHourMilliCny: 1002;
}

interface CardHourTrade {
  id: string;
  senderAccountId: string;
  receiverAccountId: string;
  cardHoursMilli: number;
  status: 'pending' | 'locked' | 'settled' | 'cancelled' | 'expired';
  idempotencyKey: string;
}
```

- 系统内商品、报价和订单只使用 `priceCardHoursMilli`、`subtotalCardHoursMilli`、`discountCardHoursMilli` 和 `chargedCardHoursMilli`。
- `amountCents`、`paymentCents` 等人民币字段只属于卡时购买、外部退款、发票和财务领域。
- 真实 GPU 用量使用 `resourceCardHoursMilli`；商品结算使用 `chargedCardHoursMilli`；账户余额使用 `availableCardHoursMilli`，三者不能混用。
- 不要创建 `includedPlatformFeeCardHoursMilli`：千分之二存在于购买卡时的人民币一侧，不属于系统内商品卡时订单。
- 可交易余额、冻结余额与待入账余额必须分列；禁止只覆盖一个总余额字段来解释交易过程。

## 6. CNY 入口边界

- 微信、支付宝等外部渠道创建的是“购买卡时”订单，不是商品订单的支付步骤。
- 支付成功后按购买订单确定的卡时数量发放；`1 卡时 = ¥1.002` 的购买单价由服务端共享实现统一计算。
- 外部支付失败、超时或退款不会改变商品订单价格；商品订单保持待结算或取消。
- 发票、支付回调和财务报表可以保留 CNY 字段，但业务商品和服务的结算 API 不接受 CNY。
- 如果保留历史人民币钱包，它只能作为“购买卡时”的资金来源之一，不能成为系统内订单的回退扣费账户。
- 卡时转让、商品交易、托管收益和设备租赁收入只记为卡时，不提供换汇、回购、提现或结算成人民币的 API。

## 7. 平台内交易规则

- 首版至少支持平台商品/服务以卡时成交、托管方以卡时获得收益，以及用户间受控卡时转让；若某一能力未接通，由 capability 隐藏入口。
- 发起方只能使用“可交易”的卡时；已过期、交易冻结、退款冻结、争议中或受限奖励卡时不能转出。
- 服务端校验租户、账户状态、余额、单笔/日累计限额、接收方状态和风险策略；客户端判断不能替代服务端校验。
- 转让和交易必须使用幂等键、乐观并发或账户行锁，并保存不可删除的双边流水、来源批次和审计事件。
- 接收方看到的单位仍是卡时。界面不得把卡时折算成“可提现人民币”，也不得使用“现金收益”文案。
- 取消、争议和退款只按原交易的卡时数逆向过账；累计逆向金额不能超过原交易，且不能把卡时退到无关账户。
- 管理员不能直接修改余额；人工调整必须走有原因、有审批、有对应科目的受控账本操作。

## 8. V1 迁移要求

`services/control-plane/src/card-hours.ts` 中 `1 卡时 = ¥1.002` 的整数换算方向符合本规范，可作为共享算法迁移基础；但 V1 仍把余额和卡时做兼容映射，并存在“卡时 → 人民币钱包”的系统内扣费回退，不能原样作为 V2 商品结算。

迁移时必须：

1. 冻结并导出每个用户的钱包、卡时批次和流水快照。
2. 把系统内商品的人民币数值一比一迁移为卡时数值，不乘或除 `1.002`。
3. 由产品/财务确认历史人民币余额如何转换或保留；不得在部署时静默重算。
4. 为迁移生成逐用户、逐批次对账报告和可逆操作记录。
5. V2 灰度期间进行双算校验，但只允许一个账本实际扣减。
6. 对账通过后关闭系统内人民币支付回退，仅保留“购买卡时”的法币入口。
7. 为历史卡时补齐可交易属性、来源批次和到期时间；没有依据的数据默认不可交易，待人工审核后再开放。

- [ ] 所有系统内商品与服务只显示并扣减卡时。
- [ ] 优惠直接减少卡时应付数，退款直接退卡时。
- [ ] 卡时不足不会自动动用人民币钱包。
- [ ] CNY 仅存在于购买卡时、外部退款、发票和财务对账流程。
- [ ] 卡时不能兑回或提现人民币，前端、API 和账本均无反向兑换路径。
- [ ] 平台内卡时转让/交易原子过账，冻结、完成、取消和超时均守恒且可审计。

- [ ] 系统内扣减、卡时购买、退款、幂等、并发余额和管理员免扣均有自动化测试。
